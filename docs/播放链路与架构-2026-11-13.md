# ColaNasOs 技术架构与影视播放链路（2026-11-13）

> 用途：把当前播放问题的完整背景交给外部评估。所有数字均为这台机器上的实测值。

## 1. 整体架构

单机 NAS 形态，没有 Docker、没有 Linux 分支，只跑 Windows。

```
┌──────────────────────────────────────────────────────────┐
│ 客户端（三种，共用一套 Flutter 代码）                      │
│  Web (dart2js)   Windows 桌面   Android                   │
│  播放器：media_kit (libmpv) + media_kit_video             │
└───────────────┬──────────────────────────────────────────┘
                │ HTTPS/HTTP + Bearer JWT（HLS 分片用 ?t= 令牌）
┌───────────────▼──────────────────────────────────────────┐
│ 内核 kernel/（TypeScript → tsc → dist/kernel）            │
│  Fastify + better-sqlite3（同步 API）+ 自研 sql 模板      │
│  端口 7788，dataDir = %APPDATA%\colanas_os_server         │
│  打包：Electron + asar（正式版），start.bat 跑源码产物     │
└───────────────┬──────────────────────────────────────────┘
                │ 子进程
┌───────────────▼──────────────────────────────────────────┐
│ sidecars/（Node 子进程，长驻）                             │
│  media（转码） ai-infer（ONNX） photo-ai indexer gpu ...   │
│  ffmpeg：vendor/ffmpeg/ffmpeg.exe（静态包，含 amf/qsv/nvenc）│
└──────────────────────────────────────────────────────────┘
```

关键约束：`better-sqlite3` 是**同步**驱动，库 307 MB。任何重查询都会直接阻塞
Node 主线程、拖慢所有并发请求（这是 2026-11-12 全站卡顿的根因，已修）。

## 3. 影视播放链路（核心）

### 3.1 会话与分段续转

1. 客户端 `POST /api/v1/player/sessions` 建会话，带 `preset`（如 `1080p_3m`）、
   `codec`、`leadMinutes`（默认 3）、可选 `startMs`。
2. 服务端把会话写进 `player_sessions`（status=pending），`pump()` 领取，最多
   `MAX_JOBS=2` 并发。
3. `runJob()` 每轮只转 **lead 段**（180 s）：
   - 输出目录 `<hls>/<session>/p0/p1/...`，每段自带 `index.m3u8` + 分片；
   - 转完一段把 status 改成 `paused`，等下一次续转。
4. 续转由客户端轮询 `GET /player/sessions?id=&pos=` 触发（`pos` = 片源绝对毫秒）。
5. 用户 seek 到未转区域 → 客户端 `_jumpTo()` **新建一个 `startMs=目标` 的会话**，
   因为顺序转码没法凭空造出后面位置的分片。

### 3.2 播放列表与分片

`buildStaticVodPlaylist()` 按**整片时长**预列全部分片，写 `PLAYLIST-TYPE:VOD` +
`#EXT-X-ENDLIST`（例如 52 分钟片 = 521 片 / 18 段）。分片 URI 带 `?part=pN&t=<token>`。

分片路由 `/api/v1/player/hls/:session/:file` 在文件不存在时会**轮询等待**
（最多 10 s），等不到返回 404 并写 `[player] 分片等待超时`。

### 3.3 转码管线（本机实测）

```
4K HEVC 片源 (3840x2160)
  → d3d11va 硬解
  → scale_d3d11 → 1920x1080 nv12
  → h264_amf（AMD Radeon 780M 硬编）
  → HLS (mpegts 或 fmp4)
pipeline = gpu-zero-copy
```

实测吞吐：**3 分钟内容 = 25~35 秒转完（约 216 fps）**，`.session.json` 记为
`{"encoder":"h264_amf","decoder":"d3d11va","pipeline":"gpu-zero-copy"}`。

也就是说硬编已经在用，转码本身不慢；慢的是**一段 3 分钟要等整段的开头**。

## 4. 当前问题与实测数据

### 4.1 播放几秒/几分钟后卡住（已修一部分）

原实现续转条件是「`pos + 90s >= 已转出末尾`」。播放器一旦缺片卡住，`pos` 不再
前进，条件永远不成立 → p1 永不产出 → 死锁。线上 13 个会话全部 `paused`、
`segments=30` 就是化石。

**已修**（提交 `5a5c980`）：
- 转完一段按 `lastPoll` 的真实位置**主动预取**（领先 1.5 段）；
- 分片路由命中「下一段未产出」时立即把会话推回 `pending`；
- 缺片等待 30 s → 10 s。

装包后日志已看到 p2→p6 连续在转，死锁解除。

### 4.2 仍然卡，4K 全屏尤其卡

| 指标 | 修复前 | 修复后（00:41 之后 1064 请求） |
| --- | --- | --- |
| P50 | 3.6 ms | 3.7 ms |
| P90 | 214 ms | **25 ms** |
| P99 | 831 ms | 831 ms |

服务端已经不卡。剩下的卡顿集中在客户端渲染：Web 端（浏览器原生 `<video>` 合成）
明显好于 Windows 桌面端（Flutter + media_kit 的 texture 合成），而全屏 4K 最差。
这是典型的「4K 窗口合成开销 + 纹理上传」特征，不是数据链路问题。

### 4.3 无法跳转

`_jumpTo()` 会新建 `startMs=目标` 的会话，但新会话的一段仍是 3 分钟，
4K 源要 25 秒才把这一段转满；客户端在等待期间没有明确的 loading 反馈，
用户看到的就是「点了没反应 / 跳不了」。

已改（未打包）：跳转会话强制 `leadMinutes=1`，首片 8 秒内落地。

## 5. 想请教外部评估的点

1. **HLS 能否不用「整片预列 + 顺序转码」这个模型**？现在播放列表承诺全片可 seek，
   但服务端只能顺序产出，语义天然矛盾。是否有更合适的方案（例如服务端按 seek
   位置切片、或改用 fMP4 + 按需 range、或直接放弃 HLS 走 HTTP Range 转封装）？
2. **4K 全屏 Flutter + media_kit 的渲染开销**：是否有比 texture 合成更省的做法
   （原生 overlay / 独立窗口 / 降 DPI 渲染），以及如何量化验证（raster 线程耗时）。
3. **一段多长最合适**：3 分钟（转 25 s）vs 1 分钟（转 8 s）vs 30 秒，在 4K HEVC
   源 + AMD 780M 上的最优取舍。
4. **能否边转边播做到「seek 后 2 秒内起播」**：例如先转低分辨率快速出片，再后台
   补高质量；或使用 ffmpeg 的 `-tune zerolatency` + 更短 GOP。
