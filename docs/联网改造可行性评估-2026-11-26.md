# 能否换成 DeepSeek 免费联网？可行性评估（2026-11-26）

> 问题：现有 AI 新闻工作流能否整套换成 DeepSeek 免费联网搜索？用省 token 的方式，达到 30 条、每条 250-300 字、各类均衡、解决"源经常不够"。
> 方法：实测两轮 PoC（全量采集+改写、按类详采+改写），全部走真实 `api.deepseek.com` / `deepseek-flash`。

## 一、直接结论

| 你的诉求 | 能做到吗 | 说明 |
| --- | --- | --- |
| 换成 DeepSeek 免费联网 | ✅ 能 | `tools:[{"type":"deepseek_web_search"}]`，服务端搜索不计费 |
| 解决"源经常不够" | ✅ 能，且效果明显 | 联网按类能搜到昨日新闻，不依赖 RSS 源可用性 |
| 各类新闻均衡 | ✅ 基本可以 | 全量实测 8 类都覆盖到了 |
| 30 条 | ⚠️ 需按类采集 | 一次全量只凑到 26 条，按类采集才稳 |
| 每条 250-300 字 | ❌ 当前模型难稳定达标 | 实测 196-223 字，这是模型倾向问题（见下） |
| 节省 token | ❌ 换成全量联网反而更贵 | 联网不省 token，省 token 要换架构（见四） |

一句话：**能用，也能解决源不够；但"全量联网"既不省 token，也达不到 250-300 字——这两点和你预期相反，需要按下面的架构来改。**

## 二、实测数据

### PoC-1：一次联网采集 8 类 + 现有 composeScript 改写
- 采集：1 次调用、8 次搜索，`prompt 9,529 + completion 2,230 = 11,759` token
- 素材：**26 条**（目标 30，一次搜 8 类太分散，每类只够 3-4 条）
- 改写：9 次调用，`prompt 15,115 + completion 5,166 = 20,281` token
- 成稿：**26 条 / 5,897 字**；单条字数 **175-259**，大多数 180-220，**无一到 250**
- **合计 32,040 token**，端到端约 45s

### PoC-2：按类详采（素材摘要 120-150 字）+ 改写目标 250-300
- 采集：2 类 6 条、4 次搜索，`10,864` token
- 素材摘要实际 **155-179 字**
- 改写：`2,105` token
- 成稿字数：**196 / 196 / 223 / 217 / 217 / 221**——**依旧没到 250**
- 合计 12,969 token / 6 条 ≈ **2,161 token/条**

## 三、三个关键发现（和直觉相反）

**1. token 不会更省，反而更高。**
联网每次搜索的结果（snippet/网页）都会拼进上下文。PoC-2 里 6 条素材光采集就花了 10,864 token。按此推 30 条全量联网约 **5-7 万 token**，而现有 RSS 方案 30 条约 **3-3.5 万**（RSS 抓取本身不花 token）。**全量联网 ≈ 现有方案的 1.5-2 倍 token。**

**2. 250-300 字是"模型倾向"问题，不是数据源问题。**
PoC-2 已经把素材喂到 155-179 字，改写仍只有 196-223 字——模型基本是"素材复述 + 一句导语 + 一句收尾"，不会主动展开到 250+。上一轮现有 RSS 方案也有 5 条只有 180-202 字。**说明 deepseek-flash 在这个改写任务上就稳定输出 180-250 字**，换数据源改变不了。

**3. 一次全量采集凑不满 30 条。**
让模型一次搜 8 类，搜索预算被摊薄，每类只搜 1 次，只拿到 26 条。**要凑 30 条必须按类分别采集**（8 次），代价是 token 更高。

## 四、真正的"省 token"架构：RSS 为主 + 联网按需补缺

不要整套换成联网。把联网当成**补源通道**，只在 RSS 缺口时启用：

```
1) RSS 抓取（0 token）—— 和现在完全一样
2) 统计每类缺口：want - 已抓到的条数
3) 只对缺口类别调用 deepseek_web_search 补素材（缺几类搜几次，缺得少就搜得少）
4) 素材凑够后，统一喂给现有 composeScript 改写（格式/校验/去重全保留）
```

这样：
- **源稳定**：哪类 RSS 抓不到就联网补哪类，不再整类空白；
- **token 增量最小**：源够时不联网，只有缺口类别付费；
- **格式不丢**：改写仍走 `json_object` 强约束，不受联网工具"不能 json_object"的限制。

另外三个省 token 的细节：
- **合并改写调用**：现在 8 类各调 1 次、重复 8 份 system prompt（约 1.5k token/份）。按"综合/科技AI/财经"合并成 3 次，省约 7-8k token。
- **利用缓存**：同一份 system prompt 重复调用可命中 DeepSeek prompt cache（`cached_tokens` 更便宜）。
- **控制搜索上下文**：补源时让模型"只返回标题+150字摘要+来源"，不要把整页正文拉进上下文。

## 五、要 30 条 250-300 字，还得解决字数

单靠换数据源不行，需要三选一（或组合）：
1. **素材加厚到 200+ 字**（含数据、背景、影响 3-5 个事实点），并给出强硬指令"不足 250 字请补充背景与影响"；
2. **对不足条目做一次"扩写"补调**（约 +30% token，但能稳定到 280 左右）；
3. **放宽到 230-270**（现有标准，更贴近 deepseek-flash 的真实能力）。

## 六、落地建议

- **短期最稳**：现有 `composeScript` 不动，只加"RSS 缺口 -> `deepseek_web_search` 补素材（摘要 150-200 字）"这一步。既解决源不够，又不破坏格式与校验。
- **中期**：按"综合/科技AI/财经"三组合并改写，配合 prompt 缓存，把 30 条的 token 压到接近现有水平。
- **字数**：先把目标定 230-270（可达），要 250-300 就对不足条目加一轮扩写补调。
- **不建议**：整套改成"全量联网 + text 模式自由输出"——token 更高、无 JSON 强约束、字数更不可控。
