# DeepSeek 内置联网搜索 vs 现有工作流：出稿对比测试（2026-11-26）

> 目标：验证「DeepSeek 接口免费自带联网搜索」是否属实，并对比它与项目现有 AI 新闻工作流在**质量**与 **token 消耗**上的差异。
> 环境：同一份系统设置（provider=deepseek / baseUrl=https://api.deepseek.com / model=deepseek-flash / key 有效）。
> 目标日期：昨天 2026-11-25。

## 一、核心问题：联网搜索真的免费了吗？

**属实，但有前提。** 实测方案A 一次请求触发了 **7 次服务端搜索**（`server_tool_use.tool_search=7`），
usage 里**没有任何按次搜索计费项**——官方 2026-11-18 起对模型自主触发的服务端搜索/抓取免收工具费，只算 Token。

但「免费」不等于零成本：
- 搜索抓回的内容会**全部拼进模型上下文**，方案A 的 7236 输入 token 里绝大部分是搜索结果；
- 省掉的是「按次搜索费」（旧价 5 元/1000 次，7 次约 ¥0.035），**推理 Token 照付**。
- 独立的 Search/Fetch API（客户端直接调用）仍按次收费，本次未用。

## 四、质量对比

**方案A（联网）优势：**
- 信息**新鲜且直接针对昨天**，不依赖 RSS 更新节奏；
- 每条自带媒体来源与日期，**可溯源**；
- 一次请求出稿，不受单个源故障影响（方案B 当天 BBC/CNA/Japan Times/Al Jazeera/DW 等境外源全部抓取失败，国际类素材明显吃紧）。

**方案A 劣势：**
- 输出是**简报体**，没有播客朗读格式（`//` 停顿、播报序号、口语化改写、点评段落）；
- 字数控制靠提示词软约束，没有硬校验；
- 是否搜索由模型判断，可能漏搜；深度思考模式可多次搜索，Token 会显著放大。

**方案B（现有工作流）优势：**
- **成熟的播客稿**：播报头、停顿标记、口语化、点评、字数硬校验、跨天去重，是为朗读场景专门打磨的；
- 分类排他、地域口径、聚合稿剔除等规则完备，事实只来自素材，幻觉风险低。

**方案B 劣势：**
- 强依赖 RSS 源可用性，境外源一挂国际类就缺料；
- 8 类各调一次 + 点评共 9 次请求，system prompt 重复 9 份，Token 是 A 的 2.2 倍；
- 抓取重试与补抓等待导致 150 s 延迟；
- 本次 5 条字数偏短（180~202 字，要求 230~270），被接受未重发。

## 五、结论与建议

1. **免费联网属实**，可以直接用 `chat/completions` + `tools:[{"type":"deepseek_web_search"}]` 开启；服务端搜索/抓取不计费，只付 Token。
2. **成本上 A 明显更划算**：1/2.2 的 Token、1/24 的耗时，还省掉了按次搜索费。
3. **质量上各有所长**：A 赢在新鲜度和可溯源，B 赢在播客朗读格式与事实约束。两者不是替代关系。
4. **工程建议**：现有工作流要把联网从「百炼 `enable_search`（按次收费）」切到「DeepSeek 内置工具」，需注意两个不兼容点：
   - 带 `deepseek_web_search` 工具时 `response_format` 必须是 `text`，**不能**用现在的 `json_object`；
   - 不能再传 `web_search_options`，`tool_choice` 也不能指定具体工具。
   因此输出 JSON 的约束要改由提示词承担（或用 Responses API），这是切换的主要改造量。
5. **推荐做法**：保留 B 的「素材→播报稿」改写与校验链路，把 A 的联网能力作为**素材补充通道**——RSS 抓不到某类时，用 `deepseek_web_search` 现搜该类的昨日新闻作为素材，再喂回 `composeScript` 改写。这样既拿到联网的新鲜度，又保住播客稿格式与事实校验。
