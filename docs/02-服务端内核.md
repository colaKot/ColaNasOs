## 5\. 服务端内核与模块规范

### 5.1 内核模块

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| `ModuleRegistry` | 显式注册模块、`dependsOn` 拓扑排序、迁移收集 | **约定式**（非 manifest，见 §5.2）；缺失/环形依赖启动期报错，单模块失败只降级自身与下游 |
| `Router` | Fastify 实例，按模块挂载 + `preHandler` 统一鉴权 | 路由用 `config.scope` 声明所需权限，内核统一校验 |
| `Auth` | JWT(HS256) + scope + 子账号 | **本项目实现**；SP0 提供 `dev-token` 逃生门，2FA/子账号在 SP3 落地 |
| `Db` | 连接 + Kysely + **MigrationRunner** | 启动即迁移 |
| `TaskQueue` | 持久化任务表 + 优先级/并发(AIMD)/暂停/进度/重试 | 统一 AI/转码/扫描/同步 |
| `EventBus` | 进程内 EventEmitter + 跨进程经 sidecar bus | 进度/通知/文件变更 |
| `ResourceMgr` | ffmpeg / **rclone（含 `serve`）** / transmission 生命周期 | 收编散落 utils；**AGPL 组件不引入** |
| `I18nRegistry` | 命名空间化键注册表 | **客户端 i18n 键由它生成** |
| `ContractRegistry` | 汇总所有 route schema → OpenAPI | **唯一真源** |
| `SidecarSupervisor` | 子进程守护/健康检查/热重启/崩溃隔离 |  |
| `Updater` | 版本目录式更新（替代 asar 原地重写） | 重启换版 |

### 5.2 域模块规范（约定式，非插件）

每个域模块 = `src/modules/<domain>/`，**自带路由/服务/仓储/迁移/i18n**：

**注册方式（v3.0 定案）**：**bootstrap 显式注册** —— `registerModules([files, photo, video, …])`，**不做目录自动扫描**。理由：显式清单可静态分析依赖与加载顺序，避免"隐式魔法"；新增域只需在清单加一项。

**跨模块调用（v3.1 定案）**：域模块之间**禁止直接 `import` 彼此的实现文件**，依赖必须显式声明并走受控通道：

-   `ServerModule.dependsOn?: string[]` 声明依赖，内核做**拓扑排序 + 启动期校验**，缺依赖直接报错；
-   跨模块能力经 `KernelApi.services.get('<moduleId>')` 取**只读服务接口**（由被依赖模块在 `register` 中 `provide`）；
-   只允许"上游依赖下游"（如 `video → files`），**禁止反向依赖与环形依赖**。

**`KernelApi` 版本化（v3.1 定案）**：`KernelApi` 是全部模块的公共契约，采用**语义化版本**（当前 `v1`）。**新增能力 = minor**；**破坏性变更 = major，且须提前至少 1 个 minor 发布弃用警告**。模块注册时声明 `kernelApi: '^1'`，不匹配则拒绝加载。

```ts
// kernel/types.ts —— 轻量描述符（无 manifest、无热插拔）
export interface ServerModule {
  id: string;                 // 'photo'
  prefix: string;             // '/api/v1/photo'
  dependsOn?: string[];       // 依赖模块 id（拓扑排序 + 环检测）
  permissions?: string[];     // 自动接权限链
  migrations?: Migration[];   // 由内核 Migrator 按 id 排序执行
  register(app: FastifyInstance, k: KernelApi): Promise<void> | void;
}

export interface KernelApi {
  db: any;                    // Kysely
  log: any;                   // Fastify / Pino logger
  events: EventBus;
  tasks: { enqueue(type: string, payload?: unknown): void };
  config: ConfigStore;
  i18n: I18nRegistry;
  contract: ContractRegistry;
}



```

-   **加载失败策略**：单模块 `register` 抛错 ⇒ 标记 `degraded` 并跳过**其下游**（`skipped`），其余模块照常加载（不阻断内核）。
-   **新增域**：加一个目录 + 在 bootstrap 注册一行（**不做自动扫描**，见上）⇒ 无需改内核逻辑。
-   **权限**：`prefix` + `permissions` 注册进内核权限表，路由中间件自动校验。

### 5.4 从零实现与阶段交付（v6.0 定案）

> 所有域模块按本蓝图**从头实现**。

| 项 | 做法 |
| --- | --- |
| 实现顺序 | 内核 → `files`（最小闭环）→ 逐域 |
| 阶段可用性 | 内核 + `files` 即可启动（功能子集），后续域逐个上线 |

| 代码来源 | 全部新写；第三方库仅从上游引入（§0.1） |

### 5.5 文件系统抽象（VirtualFS，v3.3 定案）

> ⭐ **NAS 的本质是文件**。所有域模块**禁止直接调用 `fs`**，一律经内核 `VirtualFS`。

```
kernel/vfs/
  VirtualFS       stat / list / read / write / move / copy / delete / watch
  Backend 适配器   local | smb | webdav | ftp | rclone | winfsp
  Path 规范        内部统一 POSIX 风格；Windows 盘符/UNC 在 backend 内转换
  Policy 钩子      路径级权限 · 配额 · 审计 · 软删除 · 加密空间
```

| 能力 | 说明 |
| --- | --- |
| 统一接口 | 域模块只依赖 `VirtualFS`，换后端不改业务 |
| 权限在一点 | 路径级 ACL 在 VFS 层校验，避免每个域各写一套 |
| 配额/审计 | 写入经统一出口，天然可记账 |
| 软删除 | `delete` 走回收站策略（§9.4） |
| 可测试 | backend 可 mock，业务逻辑可脱离真实 FS 单测 |

⚠️ 所有域模块**从第一天就使用 VirtualFS**；不存在绕过路径。

### 5.6 统一搜索层（v3.3 定案）

- 抽 `kernel/search`：**FTS5 + 向量（`sqlite-vec`）+ 关键词**三路，统一打分与分页。
- 各域模块注册 `index provider`（photo / video / music / book / files），内核负责调度与去重。
- 客户端只有**一个搜索入口契约**，避免"每个域一套搜索"。

## 6\. 数据层设计

### 6.1 主库选型决策（v2.1 定案）

**结论：主库维持 SQLite（better-sqlite3 + Kysely + `sqlite-vec`），不换库。**

判定依据：单机 NAS 零运维 + 当前量级（6.7 万照片 / 10 万级向量 / 数千视频）远未触及 SQLite 上限；换库收益低、成本高。**真正的问题不是"库"，而是"写模型"。**

**三条策略（比换库更划算）**：

1.  **写模型集中 + 批量写协议（v3.0 定案）**：
    -   **主库唯一写者 = 内核主进程**；sidecar **只读**，写入一律经 RPC 回写。
    -   **海量写入（indexer）走批量协议**：sidecar 本地攒批（默认 **500 行/批** 或 **2 s** 触发）→ 一次 RPC 投递 → 内核在**单个事务**内批量 `INSERT ... ON CONFLICT` 幂等写入。
    -   **参数上限**：单批参数数必须 < SQLite 999 ⇒ 500 行 × 每行 1 变量；多列写入再拆分（经验值 **400 行/批**）。
    -   **失败与进度**：批次带 `batch_id` + 序号；失败整批重投，幂等键 `(file_hash, updated_at)` ⇒ **不产生半写状态**。
    -   **不采用"多进程直接开写连接"**：WAL 下写仍串行化，且 `SQLITE_BUSY` 会把延迟抖动传导到 sidecar。
2.  **SQLite 调优**（零风险、收益立竿见影）：见 §6.4。
3.  **向量破百万再旁路**：`sqlite-vec` 先用；若向量规模破百万或查询 P99 不达标，**旁路** LanceDB / faiss 做 ANN，SQLite 仍保留元数据与业务表（**不替主库**）。

**💡 可选优化（非阻塞）—— `node:sqlite`（Node 内置）**：可**免除 `@electron/rebuild`**（直击 §15 红线 1 的工程痛点）。但**已实测 better-sqlite3 在 Electron 44 上正常**，因此它不再是"急需替代"，只是长期优化项。若要做，验证两点：① 在目标 Electron/Node 下的可用性；② **能否加载 `sqlite-vec` 扩展**。不通过就继续用 better-sqlite3，不影响路线。

**被评估但不采用**的替代：

| 方案 | 不采用原因 |
| --- | --- |
| libSQL / Turso | 原生模块需重编、生态较新；多进程写仍受限 ⇒ 收益不足以抵消迁移成本 |
| DuckDB | OLAP 列存，不适合高并发 OLTP ⇒ 仅可作**分析副库** |
| LMDB / RocksDB | 无 SQL / FTS / 向量，需自建索引 ⇒ 迁移成本过高 |
| PostgreSQL + pgvector | 需独立进程与运维，与"单机 NAS 零运维"冲突 ⇒ **不考虑** |
| Qdrant / Milvus | 独立向量服务，单机过重 ⇒ 不划算 |
| LanceDB | 无完整 SQL、生态较新 ⇒ 仅作**向量旁路**（见策略 3） |

### 6.2 Schema 策略：**按领域模型重新设计**

- **重新设计表结构**：按新架构的领域模型设计，**表名与列均为本项目定义**（附录 C 仅作"哪些数据必须建模"的参考）。
- 新项目**从零建库**，迁移脚本以"最终态"一次性创建，不背历史 `ALTER` 链。
- 需覆盖的**数据概念**（照片 / 人脸 / 场景 / 影视 / 音乐 / 书籍…）不变，但字段与索引可重新组织。

### 6.3 向量索引

| 用途 | 存储 | 检索 |
| --- | --- | --- |
| 以图搜图（CLIP 512 维） | `photo_index.clip_emb` + `sqlite-vec` 虚拟表 | ANN 近邻 + 精排 |
| 人脸检索 | 人脸 embedding + `sqlite-vec` 虚拟表 | ANN 近邻 |
| 文本语义 | `placesQuery` 词表 + 多语言 CLIP 文本塔**双路融合** | 见附录 A |

> ⛔ 不引 pgvector/HNSW（PG 专有）；用现有 `vendor/sqlite_vec`；破百万再按 §6.1 策略 3 旁路。

### 6.4 SQL 约束与调优参数

**约束**：

-   **SQLite 变量上限 999**：批量 `whereIn` 分片（400/批）。
-   索引随表建齐；大事务拆分。
-   **启动完整性**：`PRAGMA quick_check` 必须返回 ok，否则**拒绝启动**（§47）；
-   **迁移事务化**：每个迁移在独立事务中执行，失败**整体回滚**（含 `_migrations` 记录）。

**调优（建库即配置，`PRAGMA`）**：

| PRAGMA | 值 | 作用 |
| --- | --- | --- |
| `journal_mode` | `WAL` | 多读 + 单写并发 |
| `synchronous` | `NORMAL` | 显著降低写延迟（WAL 下安全） |
| `busy_timeout` | `5000` | 写锁等待，避免 `SQLITE_BUSY` |
| `mmap_size` | 视内存（如 256MB） | 减少 read 系统调用 |
| `cache_size` | 负值 KB（如 `-65536`） | 扩大页缓存 |
| `temp_store` | `MEMORY` | 临时表/排序走内存 |
| `foreign_keys` | `ON` | 外键约束 |
| 维护 | 定期 `PRAGMA optimize` | 统计信息更新，查询计划更优 |

### 6.5 客户端本地库（v2.1 定案）

**保留 SQLite，引入 Drift**（置于 `packages/nas_core`）：

-   **Drift**：类型安全 ORM + **编译期生成校验** + 内建**迁移机制**（替代手写 schema 版本号）；
-   底层仍走 **`sqlite3 3.x`**（现有本地源码编译方案保留）；
-   覆盖相册缓存、同步 baseline、播放进度等本地库。

## 7\. Sidecar 规范

### 7.1 通信协议

```ts
// NDJSON over named pipe / unix socket
interface SidecarRequest { id: string; method: string; params: unknown; }
type SidecarEvent =
  | { id: string; type: 'accepted' }
  | { id: string; type: 'progress'; payload: { percent: number; message?: string } }
  | { id: string; type: 'result'; payload: unknown }
  | { id: string; type: 'error'; payload: { code: string; message: string } };



```

-   `SidecarSupervisor`：启动、健康心跳、崩溃自动重启、优雅退出。
-   任务先落 `TaskQueue`（持久化），再投递 ⇒ **sidecar 崩溃可重投**。

### 7.2 四类 sidecar

| Sidecar | 承接 | 能力要点 |
| --- | --- | --- |
| `ai-infer` | 人脸 / OCR / 场景(CLIP) / 活动 / 检测(DETR) | ONNX Runtime；模型文件从各自上游获取，不入库 |
| `media` | 缩略图(`sharp`)、转码(`ffmpeg`)、抽帧、HDR/媒体标记 | 独立进程，仅经 CLI / 参数调用 |
| `indexer` | photo/video 索引扫描、ffprobe、MD5/phash；**已接入内核**：`k.indexer.start()/status()`（`kernel/sidecar/indexer-service.ts`）负责 `files.index` 任务，落 `files_meta` / `index_progress` | 文件监控 + 增量扫描 |
| `sync` | 同步任务执行 | 双向同步 / 冲突合并语义（ADR-0007） |

> ⚠️ `ai-infer` 的 ONNX 会话必须**串行建会话**，且 EP 白名单**显式排除 `webgpu`**（§15 红线）。

### 7.3 转码会话管理（v3.3 新增）

`media` sidecar 内建 **`TranscodeSession`**：

| 项 | 规则 |
| --- | --- |
| 会话键 | `(file_hash, quality, start_offset)` |
| 复用 | 多客户端同键**共享同一会话**（引用计数），避免重复转码 |
| 输出 | HLS 分片 + 播放列表；seek 复用已生成分片 |
| TTL | 无引用后保留 N 分钟再回收 |
| 上限 | 全局并发上限 + 按用户配额（§8） |
| 降级 | 6 处被动降级**场景**（容器不支持 / P2P 大文件 / 位图字幕等） |

### 7.4 远程访问与 P2P（v3.3 新增）

- 远程访问是**内核能力**（`kernel/remote`）：配对码、证书、NAT 穿透编排。
- 传输层复用 `node-datachannel`（现有），由独立 `p2p` 进程托管 + `SidecarSupervisor` 守护。
- 配对码仅作**通道标识**，**不作为认证凭据**（仍走 JWT/scope）。
- 中继策略、带宽上限、连接数上限纳入配置与配额。

## 8\. 任务队列规范

统一任务表 `tasks(id, type, payload, state, priority, attempts, max_attempts, progress, error, created_at, started_at, finished_at)`。

> SP0 只落最小字段集（上表）；`module_id` / `result` / `uid` / `undo_data` 等在 SP2 接 sidecar 时随迁移追加。`payload` 为 JSON 文本，`state` 取值见状态机。

-   **状态机**：`pending → running → (done | failed | canceled | paused)`。
-   **崩溃恢复（SP0 已实现）**：进程启动时 `recover()` 把 `running` 全部回滚为 `pending`，`/ready` 暴露 `tasksRecovered` 计数。
-   **优先级**：0/1/2 三档；同档 FIFO。
-   **并发**：按任务类型并发上限 + AIMD 自适应。
-   **用户配额（v3.1）**：任务按 `uid/role` 计入配额（并发数、每秒任务数、总字节），超限返回 `429` 并排队；管理员可调。
-   **暂停/恢复**：全局与按模块。
-   **进度**：sidecar 回传 → 写库 → 客户端订阅。
-   **重试**：按 `max_attempts` 重投；sidecar 崩溃任务回 `pending`。
-   **撤销**：写操作产 `undo_data`，走"预演 → 执行 → 撤销"通道（操作日志表由本项目独立设计）。

### 8.1 实现落点（2026-10-29 交付：worker 与业务收编）

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| 表结构 | `kernel/queue.ts` | 在蓝图字段上加 `next_run_at`（重试退避用），老库启动时自动补列 |
| 生产者 | `k.tasks.enqueue` / `enqueueIfIdle` | `enqueueIfIdle` 按「同 type + 同 payload 且 pending/running」去重，扫描风暴不会堆同一条任务 |
| 消费者 | 内核 worker 循环 | 模块注册完成后 `queue.start()`；`claim → handler → complete/fail`；`COLANAS_TASK_CONCURRENCY`（默认 1，上限 8）、`COLANAS_TASK_POLL_MS`（默认 500） |
| 处理器注册 | `k.tasks.register(type, handler)` | 同名重复注册**直接抛错**（启动期暴露，而不是运行期静默丢任务）；`registered()` 可查 |
| 重试 | `fail()` | `15s × 2^(attempt-1)`，上限 5 min（`COLANAS_TASK_RETRY_BASE_MS` 可覆盖测试基数）；到 `max_attempts` 落 `failed` |
| 崩溃恢复 | `recover()` | 启动时把 `running` 回滚 `pending`，`/ready` 暴露 `tasksRecovered` |
| 取消 | `POST /api/v1/tasks/cancel` + `ctx.isCanceled()` | pending 立即 `canceled`；running 由 handler 在检查点自行退出 |
| 暂停 / 恢复 | `POST /api/v1/tasks/pause` · `/resume` | body `{id}` 单条、`{type}` 按类型批量、都不传则全部 pending；`paused` 不会被 claim，`running` 不能暂停（要先 `cancel` 再重投）。返回 `{ok, affected}` |
| 进度 | `ctx.progress(pct)` | 写 `tasks.progress`，`/api/v1/tasks` 可读 |
| 已收编 | `video.subtitle.fetch`、`pt.subscription`、`files.index` | 字幕原来 `void fetch...()` 直接跑（重启即丢）；PT 订阅原来定时器就地串行执行；`files.index` 是整盘遍历（分钟级），入队后由 `enqueueIfIdle` 去重。现在都走队列 |

**还没收编的（有意保留原语义）**：

- `photo/ai/analyze` 是同步长请求（一次 HTTP 跑完整批），改队列要变成 `202 + taskId 轮询`，属 API 变更；
- `mediaTool` 自带 `jobs` 表 + 状态机 + 串行执行（等价队列），重复造反而多一层；
- `videoPlayer` 的 HLS 会话有自己的 `player_sessions` 表与生命周期（转码随会话销毁）。

## 44. AI 子系统（v8.0 新增）

> AI 是核心差异点。它不只是一个 sidecar，而是**模型 + 流水线 + 精度基线**三件套。

### 44.1 模型目录与版本管理

| 用途 | 模型 | 归属 |
| --- | --- | --- |
| 人脸检测 / 识别 | EdgeFace | `faces` |
| OCR | PP-OCR（det + rec + cls） | `ocr` |
| 场景 / 语义 | SigLIP2 + CLIP | `places` |
| 目标检测 | DETR | `places` |
| 活动识别 | 活动分类头 | `activity` |

- **模型 manifest**：`name / version / sha256 / license / size / deps`，集中登记。
- **生命周期**：下载 → 校验 → 灰度切换 → 回滚；**切换前必须先停对应 worker**（避免 ONNX 会话崩溃）。
- **目录化**：`onnx_models/<name>/<version>/`，多版本并存，按配置选活跃版本。

### 44.2 推理流水线

`预处理（解码/缩放/归一化） → 推理 → 后处理（NMS/阈值/融合） → 落库`

- 批处理：同尺寸可合批；不同尺寸分批。
- 失败重试：单张失败不阻断整批，记 `failed` 并可重跑。
- 资源：会话**串行创建**（红线 2）；EP 白名单**显式排除 `webgpu`**。

### 44.3 精度评测（防回归）

| 项 | 规则 |
| --- | --- |
| 评测集 | ≥ 150 张人工标注 + 20–30 条真实查询（可扩展） |
| 指标 | Top-5 命中率、MRR、召回率、准确率、单张耗时 |
| 铁律 | **真值只允许人工修正**；禁止用模型输出改真值后再评估（会刷出 1.000） |
| 门禁 | 任何模型/阈值变更必须跑回归；**劣化超过阈值即阻断发布** |
| 对比 | 同一评测集、同一脚本、同一判据；必要时做显著性检验 |

### 44.4 冷启动与常驻

- 热模型（人脸/OCR）**常驻**；冷模型（DETR/活动）**按需加载**。
- 首次加载超时可配；加载期间队列显示"预热中"。
- 模型文件**不进 asar**（§15 红线 5）。

## 56. 文件监控与增量扫描（v9.0 新增）

> NAS 的本质是"别人往共享目录里写文件"，**不监控外部改动，索引就是死的**。

| 来源 | 机制 |
| --- | --- |
| 本地 FS | `fs.watch`（递归）+ **去抖 500 ms** + 合批 |
| 挂载后端（SMB / WebDAV / FTP / rclone） | **轮询**（间隔可配），远程通常无可靠事件 |
| 外部删除 / 改名 | 周期性**全量 diff**（mtime + size）补齐 |

- **事件模型**：`created / modified / deleted / renamed` → 入队增量索引。
- **去重**：监控与扫描并发时，以 `mtime + size` 判断是否已处理。
- **风暴保护**：单目录事件 > N/秒 时合并为"目录级重扫"。
- **与全量扫描的关系**：监控负责"及时"，扫描负责"正确"（兜底）。

### 56.1 实现落点（2026-10-29 交付）

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 内核观测 | `kernel/fs-watch.ts` | `fs.watch` 递归 + 去抖 + 合批 + 风暴保护；**不认识任何业务表** |
| 内核轮询 | `kernel/poll.ts` | 远程根（SMB / WebDAV / rclone）周期快照 + `mtime`/`size` diff，产出同构批次 |
| 模块接线 | `src/modules/library-watch.ts` | 本地库走 `k.watch`、非本地根走 `k.poll`；事件落库 → 受影响目录增量扫描；周期全量校验 |
| 扫描入口 | `src/modules/{photo,video,music,book}/scan.ts` | 可选 `subDir`（只扫受影响目录）+ `prune`（清理磁盘已不存在的行） |
| 遍历规则 | `src/modules/files/walk.ts` | 跳过 `@eaDir` / `#recycle` / `Thumbs.db` 等（与监控共用同一份常量） |
| 事件出口 | `kernel/bus.ts` + `GET /api/v1/events/recent` | 扫描完成广播 `scan.done`；客户端按序号增量拉取做局部刷新 |

关键取舍（都有实测依据）：

- **只订阅库根，不订阅 files 根**：`filesRoot` 缺省是用户主目录，递归监视它等于监视整台机器。
- **改名降级为一删一增**：`fs.watch` 的 `rename` 拿不到旧名；下游按 `mtime + size` 幂等处理，语义等价。
- **风暴判据有两条**：事件条数（默认 > 200 条/秒）**或**受影响目录数（默认 > 16）。后者是必需的 ——
  Windows 的 recursive watcher 会把同一目录的连续写入合并上报（实测 120 个文件只报 2 条事件），
  只看条数会漏判「解压一万个文件到上千目录」这种真实风暴。
- **全局串行扫描**：媒体探测是 CPU 密集的，多个库并发扫只会互相拖慢；同一库运行中收到的新批次会合并排队。
- **目录数超过 4 个就退化为整库一次扫描**，避免一串小目录反复 walk。
- **监控不删索引**：删除事件只触发目录重扫，已索引的元数据保留（与「扫描不删已消失文件」一致，
  避免误删用户标注）。

环境变量：`COLANAS_WATCH=0` 关闭监控；`COLANAS_WATCH_DEBOUNCE_MS` 改去抖窗口（默认 500）；
`COLANAS_POLL_INTERVAL_MS` 远程轮询间隔（默认 5 分钟，`0` 关闭）；`COLANAS_MOUNT_POLL_MS` 挂载状态探测间隔（默认 10 分钟，`0` 关闭）。

验收：`npm run smoke:watch` **13/13**（不手动扫描直接丢文件即入库、子目录、非媒体与垃圾路径忽略、删除不误删、
`prune` 显式清理、事件流可拉到 `scan.done`、内核可正常关闭）；
`test/fs-watch.test.ts` + `test/poll.test.ts` 覆盖合批 / 风暴 / 忽略规则 / 快照 diff / 真实 FS 的创建与删除 / handler 抛错隔离。

### 56.2 远程轮询、外部删除与事件推送（2026-10-29 补齐）

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| 远程根轮询 | `kernel/poll.ts` → `KernelApi.poll` | SMB 视频库（`conn_type=smb` 的 UNC）由 `library-watch` 的 `remoteRootOf` 判为「非本地根」，改用轮询：首次只建基线（不发事件）、之后按 `mtime + size` 比对；连续失败 2 倍退避、上限 30 分钟；单轮差异 > 2000 条降级为整库重扫 |
| 挂载状态刷新 | `src/modules/mount` | 每 10 分钟对 `remote_mounts` 逐个探测（WebDAV `PROPFIND` / rclone `lsjson`），回写 `status / lastError / lastCheckAt` |
| 外部删除 | `scan` 的 `missing` + `prune` | **默认不删索引**（避免误删标注）；整库扫描（含每 6 小时的周期校验）统计 `missing`；显式 `POST /<domain>/scan { "prune": true }` 才清理，并级联清相册成员 / 观看进度 / 歌单成员 / 收藏·进度·归档·列表 |
| 事件推送 | `kernel/bus.ts` 环形历史 + `GET /api/v1/events/recent` | 扫描完成 `emit('scan.done', { domain, libraryId, scope, result })`；客户端按 `since/nextSeq` 增量拉取，**4 秒一轮**，失败退避到 60 s |
| 客户端刷新 | `packages/nas_core/lib/events.dart` + `apps/.../core/scan_refresh.dart` | `EventPoller` 全局一个；相册 / 影视 / 音乐 / 书房页订阅本域事件，400 ms 合并后重新 `_bootstrap()` |
| 清理入口 | 四个媒体页的「扫描」结果 | 响应带 `missing` 时 SnackBar 给「清理」动作 → 二次确认 → `prune: true`；不做静默清理 |
| 可观测 | `GET /ready` | 新增 `watch` / `poll` 统计（roots / subscribers / events / batches / storms / failures） |

取舍：
- **不做 SSE**：`Transport` 只有整包响应一种形态，引流式读取要给 Web / 桌面各写一份；
  媒体扫描是分钟级低频事件，4 秒延迟无感知，而增量拉取的请求体只有几十字节。
- **首次拉取不对齐历史事件**：`EventPoller` 第一轮只推进游标，避免页面刚打开就被旧事件触发重载。
- **周期校验只报告不清理**：`missing` 走响应与事件广播，删除必须显式 `prune` —— 网络盘短时离线不该把整库索引抹掉。
- **事件是全局的，所以去标识化**：`scan.done` 只带 `domain / libraryId / 计数`，不带库名与路径；
  登录时服务端给 token **注入 `events:read`**（不改响应里的 `scopes`），所有登录用户都能拉事件，
  具体资源仍按各自 scope 与 owner 过滤。
- **403/401 直接停轮询**：客户端 `EventPoller` 遇到权限错误不再重试（否则每轮打一次 403），下次登录重新启动。

仍缺：SMB 轮询的真机验收（当前只在本地目录上验证快照 diff，UNC 需要可用的网络共享）；
事件流不含「单个文件变更」粒度（只有库级扫描摘要）。
