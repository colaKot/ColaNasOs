# 14 导航统一设计方案（一二级菜单单一真源 + 新应用脚手架）

> 目标读者：可乐。**这是方案，不是实现**。看完请拍板 §9 的三个点。
> 现状核对日期：2026-11-03。

---

## 0. 一句话

把「一级菜单分组 / 图标 / 配色」和「二级菜单结构 / 布局」从 **Dart 里的硬编码** 搬进
`contracts/apps.json`，**生成**出类型安全的 `AppNavSpec`，配一个通用 `NasSectionShell` 组件渲染。
新增应用只需要写一段 JSON + 填生成的 4 个空方法，就跑起来一二级菜单。

## 1. 现状盘点（为什么这次溢出会修漏）

### 1.1 一级菜单：半契约驱动

`shell/app_shell.dart:155` 的 `_navGroups()`：

```dart
for (final app in _apps)                       // ← 条目来自 AppRegistry（契约生成）✓
  if (AppVisuals.groupOf(app.id) == group)     // ← 分组靠硬编码 switch ✗
    NasNavEntry(label: tr(app.nameKey), icon: AppVisuals.iconFor(app.icon), ...)
```

`shell/app_visuals.dart` 里三个 switch 把 19 个 app 全列了一遍：

| 方法 | 作用 | 漏写会怎样 |
| --- | --- | --- |
| `groupOf(appId)` | 归到 media / data / service / system | 静默落进「系统」组 |
| `iconFor(name)` | 图标 | 静默变 `Icons.apps` |
| `accentFor(appId)` | 工作台卡片渐变色 | 静默变灰色 |

### 1.2 二级菜单：复制了 4 份

| 文件 | 行数 | 定义方式 | 是否含布局代码 |
| --- | --- | --- | --- |
| `photo/photo_shell.dart` | 377 | `_NavGroup` / `_NavItem`，5 组 23 项 | ✅ |
| `video/video_shell.dart` | 975 | `_VGroup` / `_VItem`，3 组 16 项 + **动态库项** | ✅ |
| `music/music_shell.dart` | 780 | `_MGroup` / `_MItem`，3 组 9 项 | ✅ |
| `discover/discover_shell.dart` | ~330 | Hub + Tab（形态不同） | — |

「布局代码」= `SizedBox(width: _collapsed ? 56 : 128)` + 折叠头 Row + ListView +
选中态 + hover + 拖动滚动条抑制。**三份逐字重复**。

### 1.3 这次的 4px 溢出就是活证据

`RenderFlex overflowed by 4.0 pixels` 出在折叠头 Row：56 宽侧栏下可用宽度 36px，
而默认 `IconButton` 最小 48。我上次只修了 `video_shell` 和 `photo_shell`，
**`music_shell:116` 有完全相同的代码，仍在溢出**。

> 这不是疏忽，是结构性问题：同一个 bug 有三份副本，改一份不可能记得另外两份。

## 2. 目标 / 非目标

### 目标

1. **单一真源**：一二级菜单结构只在 `contracts/apps.json` 写一次。
2. **新增应用零布局代码**：加一段 JSON → 生成骨架 → 填内容方法，菜单自动出现。
3. **同类 bug 只有一处可能**：布局只有 `NasSectionShell` 一份实现。
4. **不会静默漏页面**：契约里的每个 section 必须有实现，缺了门禁直接失败。
5. **可回归**：一个遍历式 widget 测试覆盖「所有 app × 所有 section × 三种宽度 × 折叠两态」。

### 非目标（明确不做，避免方案膨胀）

| 不做 | 原因 |
| --- | --- |
| 运行时由服务端下发菜单结构 | 菜单是编译期结构，改一次要走发版；动态下发会让「找不到页面」变成运行时错误 |
| 用户自定义排序 / 隐藏菜单项 | 另一个特性（需要 per-user 配置表），与本次正交 |
| 不同端用不同菜单结构 | 端差异只体现在**可见性**（能力矩阵），不改结构；否则测试矩阵爆炸 |
| 一次性改造 discover 的 Hub 形态 | 它本来就不是侧栏导航，先留 `style: "hub"` 逃生舱 |

## 3. 设计：三层

```
contracts/apps.json          ← 唯一真源（人手写）
        │
        │  npm run gen
        ▼
packages/nas_core/lib/
  app_registry.dart          ← 已有：应用清单
  app_nav_spec.dart          ← 新增：菜单结构（只读数据 + section id 常量）
apps/colanas_os/lib/shell/
  app_nav_registry.g.dart    ← 新增：AppNavSpec 实例 + 与 builder 的对账表
        │
        ▼
nas_ui/lib/src/nav/
  nas_section_shell.dart     ← 新增：唯一的一二级菜单渲染实现
```

### 3.1 契约形状（`contracts/apps.json`）

```jsonc
{
  "id": "video",
  "nameKey": "app.video",
  "route": "/video",
  "icon": "movie",                    // 已有，iconFor 用它（不再按 appId 硬编码）
  "group": "media",                   // ★ 新增：替代 groupOf 的 switch
  "accent": ["#6366F1", "#9F7AEA"],   // ★ 新增：替代 accentFor 的 switch
  "endpoints": ["desktop", "web", "..."],

  "nav": {                            // ★ 新增：二级菜单
    "style": "side",                  // side（侧栏）| hub（发现页那种）| none
    "collapsedWidth": 56,             // 可选，默认 56
    "expandedWidth": 128,             // 可选，默认 128
    "sections": [
      { "id": "libraries",
        "titleKey": "video.nav.libraries",
        "icon": "movie",
        "items": [
          { "id": "home", "labelKey": "video.nav.home", "icon": "home" },

          // 动态项：结构在契约里，数据运行时来
          { "id": "lib", "dynamic": "video.libraries",
            "labelFrom": "name", "iconsFrom": "libType",
            "idPrefix": "lib:" },

          { "id": "history", "labelKey": "video.nav.history", "icon": "history" }
        ]
      },
      { "id": "collections",
        "titleKey": "video.collection.group",
        "icon": "collections",
        "items": [
          { "id": "collections", "labelKey": "video.collection.title", "icon": "collections" },
          { "id": "smartAlbums", "labelKey": "video.smart.title", "icon": "sparkles" },
          { "id": "duplicates",  "labelKey": "video.duplicate.title", "icon": "copy" }
        ]
      }
    ]
  }
}
```

支持的两个变量点，正好覆盖现有全部需求：

| 变量 | 用途 | 现有例子 |
| --- | --- | --- |
| `dynamic` + `labelFrom` / `iconsFrom` | 运行时数据撑开菜单项 | 影视的库列表（`lib:` 前缀）、相册的相册列表 |
| `items[].when` | 条件显示 | 影视的「日本榜单」只在有日系库时出现（`when: "hasJpLibrary"`，由 builder 侧提供布尔） |

### 3.3 组件 API（`nas_ui/nas_section_shell.dart`）

```dart
NasSectionShell(
  spec: kAppNavSpecs['video']!,
  selectedId: _key,
  onSelect: (id) => setState(() => _key = id),
  controller: _navController,        // 折叠状态（持久化到 SettingsStore）
  dynamicItems: {                    // 动态项数据，只有用到时才需要给
    'video.libraries': [
      for (final lib in _libraries)
        NasDynamicNavItem(id: 'lib:${lib.id}', label: lib.name, icon: _iconOf(lib.libType)),
    ],
  },
  conditions: {'hasJpLibrary': _hasJpLibrary},
  builder: (context, sectionId) => switch (sectionId) {
    'home' => const VideoHomePage(embedded: true),
    'lib' => VideoPage(embedded: true, libraryId: ctx.libraryId),
    // ...
  },
)
```

内部职责（**这些以后再也不用各模块各写一遍**）：

- 56 / 128 两态 + 折叠按钮（`32×32` 紧凑约束、`MainAxisAlignment.center`）——**这次溢出的修法固化成唯一实现**
- 分组标题 + 图标 + 选中态 + hover + 滚动条抑制
- 窄屏（< 720）：侧栏收成顶部横向 Tab（或 Drawer），不是把 56px 硬塞
- 折叠状态持久化（`ui.nav.collapsed.<appId>`）
- 溢出防护：`LayoutBuilder` 断言 `maxWidth >= 折叠按钮所需宽度`，超了在 debug 下 `assert` 报出**具体是哪个 spec**

### 3.4 新增应用的完整流程（用户最关心的那条）

```bash
# 1. 契约加一条（约 30 行 JSON）
#    contracts/apps.json  →  "id": "nvr", "group": "service", "nav": {...}
#    contracts/i18n.json  →  "app.nvr": {}, "nvr.nav.cameras": {}, "nvr.nav.recordings": {}
#    contracts/messages/zh-CN.json / en-US.json → 对应译文

# 2. 生成
npm run gen          # AppRegistry + AppNavSpec + i18n 常量
npm run gen:client   # 若新增了后端接口

# 3. 生成器会建好 4 个空壳（已存在则跳过，不覆盖）
#    lib/features/nvr/sections/cameras_section.dart      ← 只有一行 TODO + 空占位组件
#    lib/features/nvr/sections/recordings_section.dart
#    lib/features/nvr/nvr_shell.dart                     ← 已接好 NasSectionShell

# 4. 填内容。没填的（还是空占位）会被门禁挡：
npm run gen:apps.check   # 缺实现 → 直接失败并列出缺哪个 section
```

第 4 步的「挡住」是**关键设计**：`kImplementedSections` 由生成器与手写注册表对账，
少一个就红。这样「新增了系统但页面忘了接」不可能静默上线。

## 6. 取舍说明（为什么不选别的写法）

| 备选 | 为什么不选 |
| --- | --- |
| **每个模块继承一个 `BaseShellPage`** | Dart 单继承，且 shell 里要混业务状态（影视的库列表、相册的 AI 状态）；继承会把状态和布局搅一起。组合（`NasSectionShell` 作为子组件）更干净 |
| **用 GoRouter / Navigator 2.0 的嵌套路由表达菜单** | 菜单是「同一页面内的分区切换」，不是路由。做成路由会丢失「切分区不重建外层」的性能优势，且深链接需求目前没有 |
| **菜单结构由服务端下发（运行时可变）** | 见非目标：会让「菜单有项但没实现」变成运行时崩溃；且每次改菜单要动服务端契约 + 缓存 |
| **只抽布局、菜单仍各写各的** | 解决不了「新增 app 要手写菜单」和「section 漏实现没人发现」，而这两条正是你提的诉求 |
| **代码生成整页（含内容）** | 页面内容无法生成，只能给空壳；所以方案止步于「空壳 + 对账」，不做「生成业务逻辑」 |

## 8. 风险

| 风险 | 缓解 |
| --- | --- |
| 迁移期新旧两套并存，行为不一致 | 按模块整块切换（music → photo → video），不混用；每步单独验收 |
| 影视的 `lib:` 动态项语义特殊（`id` 前缀拼库 id） | 契约用 `idPrefix` 显式声明，组件不猜 |
| 相册 23 项的选中键有历史包袱（`settings.library` 这种带点的） | section id 保持原样不动，只是搬进契约；不做「顺手重命名」 |
| 生成器改契约会影响 `gen:apps.check` 既有测试 | 新增校验写成独立 step，失败信息带文件名与 section id |
| 折叠态宽度 56 是硬编码常量，未来设计改宽度 | 契约里给出 `collapsedWidth` / `expandedWidth`，组件读它而不是常量 |

## 9. 需要你拍板的三点

1. **`group` 用枚举还是自由字符串？**
   建议**枚举**（`media` / `data` / `service` / `system`，就是现在这四个 `nav.group.*`），
   生成器校验取值，写错直接红。自由字符串会导致「新增分组忘了加 i18n」这种低级错。

2. **新增应用时，生成器要不要直接改 `pubspec` / 路由表？**
   建议**不要**。脚手架只建 `lib/features/<id>/` 目录与空壳，路由注册保留手写一处
   （`app_shell._content` 的 switch）—— 生成器改构建配置的坑远比省下的两行多。

3. **discover 的 Hub 形态什么时候统一？**
   建议**本次不动**（先 `style: "hub"` 绕过），等一二级稳定后再单独评估要不要把它也做成侧栏。
   如果你希望这次一起统一，我需要先确认「豆瓣 / PT / 影视发现」三个 Tab 是否要变成二级导航项。
